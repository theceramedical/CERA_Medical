# Single production host setup

The repository builds six images: web, API, worker, CMS, commerce (also runs the commerce worker), and migrator. The production workflow compiles public URLs and publishes immutable commit tags. The host resolves those tags to registry digests before starting containers. No deployment is considered successful until the host health gate and the external read-only smoke test pass. The staging workflow remains available but is not part of the chosen one-server rollout.

## Before the first deployment

1. Provision one production Linux host with Docker Compose and `age`. Open only TCP 80 and 443 to the public. Allow SSH only from the administrator or CI source. Give the deployment user Docker access and write access to `/opt/cera`.
2. Create `/opt/cera/.env` mode 600 on the host. Start from `.env.example`, but use unique non-placeholder production values. Set `NODE_ENV=production`, `CERA_ENV=production`, `CERA_DOMAIN`, `DATABASE_URL` and `CMS_DATABASE_URL` with `postgres` as the host, `VALKEY_URL=redis://valkey:6379/0`, `VALKEY_HOST=valkey`, and `POSTGRES_HOST=postgres`. Set all application, Authentik, R2, Resend, and ERPNext values. URL-encode special characters in database URL credentials. The public web and API URLs must match the CI build variables.
3. Provision DNS for `www`, apex, `api`, `admin`, `catalogue`, `auth`, and `crm` under `CERA_DOMAIN`. Caddy manages TLS certificates and stores them in a persistent volume.
4. Keep the age identity **off the host**. Put its public key in `BACKUP_AGE_PUBLIC_KEY` in `.env`. Encrypted database dumps stay in `BACKUP_TARGET_DIR` on this host; leave `BACKUP_OFFSITE_REMOTE` unset and do not create `/opt/cera/.backup-remote`. This is not a disaster-recovery backup: loss, compromise, or deletion of the server can also destroy its backups. Enable versioning on the R2 media bucket separately; database dumps do not include uploaded media.
   Install `infra/systemd/cera-backup@.service` and `infra/systemd/cera-backup@.timer` under `/etc/systemd/system`, then enable `cera-backup@production.timer`. Test one manual run and a restore before relying on the timer. The script prunes local encrypted dumps after `BACKUP_RETENTION_DAYS`.
5. Allow the host to pull private GHCR images (`docker login ghcr.io`) using a read-only package token. Set GitHub environment secrets `PRODUCTION_HOST`, `PRODUCTION_USER`, `PRODUCTION_SSH_KEY`, and `PRODUCTION_KNOWN_HOSTS`. `PRODUCTION_KNOWN_HOSTS` must contain the verified SSH host key; do not derive it from an unverified first connection. Set environment variables `PRODUCTION_SITE_URL`, `PRODUCTION_API_URL`, `PRODUCTION_CMS_URL`, and `PRODUCTION_MEDIA_URL`. Protect the production GitHub environment with required reviewers.
6. Install ERPNext using its official Frappe Docker production Compose files with `infra/erpnext/compose.cera.yaml` as an additional overlay. Start CERA Compose first so the `cera_cera-public` network exists. Keep ERPNext's MariaDB and Redis on its private Compose network; only its frontend joins the CERA public Docker network. Create the ERPNext site named `crm.<CERA_DOMAIN>`, complete setup, set `FRAPPE_SITE_NAME_HEADER=crm.<CERA_DOMAIN>` in Frappe Docker, and use `http://erpnext-frontend:8080` as the worker's `ERPNEXT_URL`. Follow `docs/runbooks/erpnext.md` for fields, token, and verification. Size the single host for both stacks before accepting traffic.
7. Review and commit the generated Payload and Vendure initial migrations. Both applied to fresh local test databases; rehearse the full migrator and a timed `restore.sh` against an isolated local copy before the first production release. The migrator refuses to build or run if either migration directory is empty.

## Release and recovery

A `v*.*.*` tag builds production-specific images and deploys after GitHub environment approval. The workflow transfers only Compose and infrastructure scripts; `/opt/cera/.env`, GHCR credentials, and backup keys remain on the host. The deploy script backs up all five databases locally, runs the migrator once, starts the six application processes, checks health, and retains `.release.previous.env` for image rollback.

On the host, `bash infra/scripts/rollback.sh production` restores the prior images. Database migrations are forward-only and may make old images incompatible; inspect the failed migration and prefer a forward repair. To rehearse restore, use an isolated host with its own `.env`, set `BACKUP_AGE_IDENTITY_FILE` to the private key path and `RESTORE_CONFIRM=restore:staging:cera_app`, then run `bash infra/scripts/restore.sh staging cera_app /path/to/file.dump.age`. Restore replaces data in the named database and verifies that public-schema tables are present. Repeat for the other four databases and record elapsed time, application checks, and row counts.

The workflows fail when the host secrets are absent. They do not mark an unperformed deployment as successful.
